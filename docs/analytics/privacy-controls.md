# Site consent controls

Site settings include **Require visitor consent**. When enabled, every JavaScript installation snippet generated by the integration page—including Web Vitals, heatmaps, experiments, Tag Manager and its live-preview snippet—sets `data-require-consent="true"`. The tracker does not persist visitor/session/recording identifiers, install content/search/download listeners, load optional analytics configuration, or queue analytics while a required choice is undecided or denied. The no-JavaScript image fallback is deliberately disabled because it cannot present the choice first.

The Integration → **Consent & privacy** tab provides a copyable, accessible accept/reject banner and a persistent privacy-settings button. The example asks for one choice covering anonymous analytics and the site's enabled behaviour tools. Adapt its text and presentation to the site's actual purposes and legal notice; this starter is not legal advice and does not replace a jurisdiction-specific consent-management platform.

```js
SeeRay.getConsentState(trackingId); // 'unknown', 'granted', or 'denied'
SeeRay.setConsent(true, trackingId); // accept only this site
SeeRay.optOut(trackingId); // withdraw and stop only this site
```

Calling `SeeRay.optOut()` without a Tracking ID withdraws consent for every tracker instance on the page. A stored denial remains effective even if the site owner later makes consent optional. Withdrawal discards queued events and behaviour data, stops recordings, removes this site's tracker-owned local/session storage keys (including visitor and experiment assignments), and keeps only the denial choice when storage is available. If the site does not require consent, tracking remains active by default until a visitor explicitly opts out. Do Not Track continues to suppress collection independently.

The site policy is returned to authorized site-management APIs and its changes are covered by the site's metadata-only configuration audit event (the policy value itself is not copied into that log). It controls generated installation guidance; as with any public JavaScript tracker, a site owner who manually removes the consent attribute or calls the collector directly can bypass the browser-side prompt.

## Hosted privacy preferences

Integration → **Consent & privacy** can generate an embeddable hosted preferences control. It is a complete snippet containing the tracker and an iframe from `/privacy/preferences?siteId=...`; place both on the same customer page. The hosted control asks the tracker on that page for the current state, and its Allow/Opt out actions update that same site's tracker. The preference page itself does not send analytics or identify the visitor.

This iframe bridge is necessary because browser storage is origin-scoped: a page hosted on the analytics service cannot directly change local storage on a customer's website. Messages are accepted only from the analytics origin, from the exact preferences iframe path, and for the matching tracking ID. The site should serve the tracker and iframe together; opening the hosted URL by itself displays that it is not connected and does not claim to change consent. The choice remains local to that browser and site, not a server-side identity record.

The hosted page is public and embeddable by design; its response uses a restrictive content-security policy, no-referrer policy, no-store caching, and validates that the tracking ID belongs to an enabled site. As with the starter banner, adapt privacy text and use only where the site's notice and legal requirements permit.

Run the Chromium browser acceptance with `npm --prefix tracker run test:e2e:privacy` (from `tracker/`, install Chromium once with `npx playwright install chromium`). It loads the published tracker and hosted-page assets on distinct origins and verifies consent gating, cross-origin allow/withdraw, persistence, identity cleanup, and collection stopping. Its fixture uses a test analytics server and a valid synthetic site ID; the Quarkus integration test separately verifies the database-backed active-site endpoint. Production-host deployment and assistive-technology acceptance remain separate checks.

For authenticated cross-device visitor timelines, see [cross-device visitor profiles](visitor-identities.md). User IDs are optional and must be opaque, non-personal application identifiers; the browser integration must wait for both login and consent.

## Fingerprint risk detection

Site settings can enable **Browser fingerprint risk detection** separately from ordinary analytics. The feature is disabled by default and affects neither visitor counts nor visitor/User ID merging. A generated Web Tracker snippet then uses `data-fingerprint-risk="true"`; replace installed snippets after changing the setting.

When enabled, the tracker derives a local signal from browser rendering and environment capabilities, sends only a versioned short hash, and never sends the canvas output, renderer value, font measurements, or hardware values. If the site requires consent, the signal is created and sent only after consent; DNT and withdrawal suppress it. SeeRay stores the signal as a site-scoped, non-reversible risk key for the configured retention period and exposes only related-visitor/account counts, evidence types, and confidence to the management UI.

The collector can also record a JA4 TLS client fingerprint supplied by a trusted edge proxy. Enable this server-side with `SEERAY_JA4_FINGERPRINT_ENABLED=true`, set `SEERAY_GEO_TRUSTED_PROXY_CIDRS` to the exact immediate proxy CIDRs, and configure that proxy to overwrite `cf-ja4` on origin requests. The same site-level **Fingerprint risk detection** switch must be enabled. If the site requires consent, SeeRay collects JA4 only on tracker events carrying the post-consent browser signal; the JavaScript-free pixel path does not collect JA4 for those sites. For Cloudflare, the `cf-ja4` origin header is provided by the **Add bot management headers to origin** managed transform and requires an eligible Bot Management configuration; see [Cloudflare's managed transforms](https://developers.cloudflare.com/rules/transform/managed-transforms/reference/) and [JA3/JA4 fingerprint documentation](https://developers.cloudflare.com/bots/additional-configurations/ja3-ja4-fingerprint/). Never accept this header from arbitrary clients or enable this collection on a directly reachable origin.

JA4 describes a TLS client pattern and is shared by many people using common browsers, operating systems, or automation. A JA4-only match is marked low confidence and can indicate related visitors/accounts, but cannot establish that they belong to the same person. Browser and JA4 values are compared independently; matching signals do not merge visitor IDs, profiles, or accounts and must not be used alone for account enforcement.

The Live and Visitors views can display a numeric client IP and group visits by IP, JA4 TLS fingerprint, or browser fingerprint. IP collection applies only to accepted tracking events and follows a 30-day retention policy on raw events/session records, cleared by the daily retention job; it does not affect visitor identity or aggregate analytics. SeeRay resolves direct socket peers itself and trusts `CF-Connecting-IP` or `X-Real-IP` only when the immediate peer is in `SEERAY_GEO_TRUSTED_PROXY_CIDRS`. It ignores untrusted forwarding headers. Consent-required JavaScript-free pixel events do not retain IP. Fingerprint views return per-result group labels, not fingerprint keys. Grouping is a UI aid and never merges visitor/account identities.
